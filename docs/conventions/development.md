# Development Conventions

## 공통 원칙

- 한 변경은 한 가지 목적에 집중하고 작게 유지한다.
- 명확한 코드를 우선하며, 조기 추상화와 사용하지 않는 확장 지점을 만들지 않는다.
- 새 의존성을 추가하기 전에 표준 라이브러리와 기존 의존성으로 해결 가능한지 확인한다.
- 사용자 입력과 외부 응답은 경계에서 검증한다.
- 비밀값, 토큰, 개인정보를 코드·로그·테스트 픽스처에 넣지 않는다.

## 코드 스타일

- 프로젝트에 채택한 formatter와 linter의 결과를 기준으로 한다.
- 이름은 역할과 의도를 드러내고, 축약어는 도메인에서 널리 쓰이는 경우만 사용한다.
- 함수와 모듈은 하나의 책임을 갖도록 유지한다.
- 주석은 코드가 무엇을 하는지보다 결정의 이유와 제약을 설명한다.
- 언어별 세부 규칙은 스택 확정 후 각 앱 README에 명시한다.

## 오류와 API

- 오류를 삼키지 말고 호출자가 처리 가능한 형태로 전달한다.
- 사용자용 메시지와 내부 디버깅 정보를 분리한다.
- API 응답과 오류 형식은 일관되게 유지하고 계약 변경은 문서와 함께 반영한다.
- 로그에는 요청 추적에 필요한 문맥을 포함하되 민감정보는 제외한다.

## 테스트 주도 개발과 검증

- 개발은 TDD(Test-Driven Development)를 기본 방식으로 한다. 동작을 변경할 때는 실패하는 테스트를 먼저 작성하고, 테스트를 통과하는 최소 구현을 만든 뒤, 동작을 유지하며 리팩터링한다.
- 테스트는 요구사항과 실패 위험을 확인할 수 있는 가장 작은 범위로 작성한다. 핵심 비즈니스 규칙과 재발 가능성이 높은 버그를 우선 보호한다.
- 빠른 개발을 위해 과도한 테스트는 금지한다. 프레임워크나 외부 라이브러리 자체의 동작, 단순한 getter·setter와 상수, 구현 세부사항, 동일 동작의 중복 조합은 테스트하지 않는다.
- 통합 및 E2E 테스트는 단위 테스트만으로 확인할 수 없는 경계와 핵심 사용자 흐름에 한정한다. 모든 경우의 수를 자동화하려 하지 않는다.
- 탐색용 프로토타입, 단순 설정·문서 변경, 자동화 비용이 효과보다 큰 UI 표현은 TDD 대상에서 제외할 수 있다. 이 경우 핵심 동작은 재현 가능한 수동 절차로 검증하고 PR에 결과를 기록한다.
- PR 전 변경 영역의 formatter, linter, typecheck와 관련 테스트만 우선 실행한다. 전체 테스트는 변경 영향이 넓거나 CI에서 요구할 때 실행한다.

## 환경 설정

- 로컬 설정 예시는 `.env.example`에 키 이름과 안전한 예시값으로 제공한다.
- 실제 `.env` 파일은 커밋하지 않는다.
- 새 환경 변수는 사용하는 앱 README와 배포 설정에 동시에 문서화한다.

## 문서 동기화

- 요구사항, API 계약, 아키텍처, 실행 방법에 영향을 주는 코드 변경은 관련 문서를 같은 PR에서 갱신한다.
- 중요한 기술 선택은 [`../decisions/`](../decisions/README.md)에 ADR로 기록한다.
